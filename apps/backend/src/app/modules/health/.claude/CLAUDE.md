# Модуль `health`

Три ручки о состоянии самого сервиса. Бизнес-данных модуль не трогает.

| Ручка            | Что отвечает                                              | Кто спрашивает            |
| ---------------- | --------------------------------------------------------- | ------------------------- |
| `GET /health/live`  | процесс жив, event loop крутится                         | docker/kubernetes liveness |
| `GET /health/ready` | база, брокер и объектное хранилище отвечают              | балансировщик, readiness   |
| `GET /health/info`  | имя, версия, окружение, ревизия схемы БД                 | человек и выкатка          |

## live против ready — путать нельзя

**`/health/live` не ходит никуда.** Он отвечает 200 всегда, пока процесс
способен выполнить корутину. Провал liveness означает «контейнер сломан,
перезапусти его». Если повесить сюда проверку базы, то падение Postgres
перезапустит все контейнеры приложения сразу: перезапуск базу не чинит, а
сервис теряет прогретые пулы и не может даже доложить о проблеме. Кратковременная
недоступность базы превращается в непрерывный цикл рестартов.

**`/health/ready` ходит во все зависимости.** Провал readiness означает
«процесс жив, но обслуживать запросы сейчас не может»: оркестратор выводит его
из балансировки и вернёт обратно, когда зависимость поднимется. Контейнер при
этом не перезапускается и не теряет состояние.

Отсюда правила, которые нельзя нарушать:

- в `/health/live` не появляется ни одной зависимости;
- healthcheck в `docker-compose.yml` и `livenessProbe` в kubernetes смотрят на
  `/health/live`, `readinessProbe` — на `/health/ready`;
- `/health/ready` отвечает 200 или 503 и **никогда не кидает исключение**:
  ответ 500 вместо отчёта лишает дежурного информации ровно тогда, когда она
  нужна.

## Чего в модуле нет и почему

Набор файлов определяется содержанием модуля, а не шаблоном каталога. В
`health` нет:

- `models/` — модуль не владеет ни одной таблицей. Он читает `alembic_version`
  сырым SQL, потому что это чужая служебная таблица Alembic, а не его модель;
- `schemas/requests.py` — ни одна ручка не принимает ни тела, ни параметров;
- `subscribers.py` — модуль не подписан на доменные события;
- `tasks.py` и `consumers` — фоновой работы у модуля нет. Проверка состояния,
  порождающая фоновую работу, перестаёт быть проверкой.

Пустые файлы и пустые пакеты вместо этого списка заводить не надо: заглушка
выглядит как незаконченная работа и провоцирует «дописать логику» туда, где её
не должно быть.

## Устройство

```
handlers.py            # только HTTP: собрать ответ, выставить статус и заголовки
services.py            # вся логика: проверки, таймауты, чтение ревизии
schemas/responses.py   # контракт ответов
module.py              # манифест Module + lifespan с клиентами проверок
```

- `handlers.py` не знает ни про aio-pika, ни про botocore: он получает `Probes`
  из `app.state` и передаёт их сервису.
- `services.py` не создаёт клиентов — они приходят аргументом. Соединение с
  брокером и клиент S3 создаёт `Module.lifespan` один раз на процесс:
  readiness опрашивают раз в несколько секунд, и соединение на каждый опрос
  стоило бы дороже самой проверки.
- Приложение обязано подниматься при лежащем брокере или хранилище. Если
  падение зависимости уронит старт, readiness не сможет о нём доложить.
  Соединение с брокером восстанавливается лениво при очередной проверке.
- Псевдоним `RoSession` объявлен в `handlers.py`, а не взят из `app.api.deps`:
  правило зависимостей `api → modules → platform → kernel` запрещает модулю
  импортировать слой api.

## Проверки обязаны действительно ловить отказ

- **Брокер.** `connection.is_closed` врёт: robust-соединение переподключается
  само и до первой неудачной операции считает себя живым. Проверка открывает
  канал — это настоящий round-trip к брокеру. Не заменяй её на проверку флага.
  Подключение в `BrokerProbe` идёт под `asyncio.Lock`: readiness дёргают
  оркестратор, балансировщик и мониторинг независимо, и без замка наложившиеся
  проверки завели бы по своему соединению, а лишние остались бы висеть и
  переподключаться фоном до конца жизни процесса. Замок снимать нельзя.
- **Хранилище.** `head_bucket` по бакету сервиса, а не `list_buckets`: в проде
  у сервиса ключи с доступом только к своему бакету, и листинг всех бакетов
  вернул бы им `AccessDenied` — readiness горел бы красным на исправном
  хранилище. Побочная польза: проверка ловит опечатку в имени бакета.
- **База.** `SELECT 1` через RO-сессию: проверяется, что пул выдаёт соединение
  и база на нём отвечает.
- У каждой проверки свой таймаут (`HEALTH_*_TIMEOUT`), проверки выполняются
  параллельно. Последовательный опрос складывал бы таймауты, и три
  зависимости держали бы ответ втрое дольше любой из них.

## Формат ответа readiness

Обычная схема ответа, а не `application/problem+json`. Неготовность — это
отчёт о состоянии, а не ошибка обращения: клиент ничего не сделал не так и
исправлять ему нечего. В problem+json детализация по зависимостям уехала бы в
произвольные дополнительные члены, которых нет ни в схеме, ни в OpenAPI.

Ответ помечен `Cache-Control: no-store`. Прокси, закешировавший 200 хотя бы на
минуту, продолжит слать трафик в контейнер, который уже доложил о неготовности.

## Стоит ли `/health/info` быть публичным

Вывод: **нет, в проде его надо закрывать на периметре.** Версия сборки и
окружение — это разведданные: по ним подбирают известные уязвимости именно этой
версии. Секретов ручка не отдаёт (ни DSN, ни ключей, ни адресов зависимостей) —
поэтому её открытость не авария, а лишняя подсказка.

Пока в шаблоне нет слоя аутентификации, ручка открыта: закрывать её
самодельной проверкой в модуле хуже, чем оставить открытой и закрыть там, где
это делается правильно. Рекомендация для боевой установки — не пускать
`/health/info` (и `/health/ready`) снаружи через Caddy/nginx или потребовать
аутентификацию, когда появится модуль авторизации.

## Команды

```bash
uv run pytest tests/test_health.py -v          # тесты модуля
curl -s localhost:8000/health/live             # 200 всегда, пока процесс жив
curl -si localhost:8000/health/ready | head -1 # 200 или 503
curl -s localhost:8000/health/info             # revision = null, если БД недоступна
docker compose ps                              # api healthy = /health/live отвечает
```

## Если правишь модуль

- Новая зависимость сервиса → новая проверка в `check_readiness` и новый
  таймаут в `HealthSettings` и `.env.example`; клиент создаётся в lifespan,
  а не в проверке.
- Проверка обязана быть только чтением. Ручка, которая пишет, — это уже не
  health.
- Не добавляй в `/health/info` ничего, что нельзя опубликовать: ручка
  отвечает без аутентификации.
