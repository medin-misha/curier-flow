# Побочный эффект: чем его делать

В шаблоне четыре механизма, и они не взаимозаменяемы. Выбор делается **до**
того, как появился файл, поэтому он живёт здесь, а не в правиле по пути.

Инварианты каждого механизма — в правилах, они подтянутся сами, когда откроешь
нужный файл: `.claude/rules/events.md` (события и подписчики),
`.claude/rules/background-work.md` (TaskIQ против RabbitMQ),
`.claude/rules/transactions.md` (границы транзакции).

## Шаг 1. Выбери механизм

Отвечай на вопросы сверху вниз, первый утвердительный ответ и есть решение.

```
Эффект приходит извне (сообщение чужого сервиса)?
  └─ да ──► консьюмер RabbitMQ        → consumers.py + topology/consumers в манифесте
  └─ нет
      │
      ▼
Эффект нельзя потерять (письмо, списание, синхронизация с чужой системой)?
  └─ да ──► emit(session, Event(...))  → events.py, подписчик в subscribers.py слушателя
  └─ нет
      │
      ▼
Эффект нужен по расписанию или отложенно, а не в ответ на факт?
  └─ да ──► TaskIQ                     → tasks.py + tasks в манифесте
  └─ нет
      │
      ▼
Потерю переживём (прогрев кеша, метрика, необязательный пинг)?
  └─ да ──► after_commit(session, fn)
```

Проверочный вопрос для развилки «нельзя потерять»: **«а если этот эффект не
случится?»** Ответ длиннее одного слова — значит `emit()`.

Ни один из механизмов **не привязан к HTTP-статусу**. Триггер — успешный
коммит, решает транзакция, а не то, что ручка вернула 201.

| Механизм | Гарантия |
| --- | --- |
| `emit(session, Event(...))` | at-least-once: строка в outbox коммитится вместе с данными, публикует релей |
| `after_commit(session, fn)` | никаких: процесс, упавший между коммитом и хуком, потеряет его молча |
| TaskIQ `@schedule(...)` | наш формат, наш планировщик; переживает параллельный запуск в нескольких воркерах |
| Консьюмер RabbitMQ | чужой контракт, at-least-once, обязателен `run_once` по `processed_messages` |

## Шаг 2. Подключи

### `emit()` — факт, который нельзя потерять

Событие объявляется в `events.py` **модуля-владельца**, вызывается из
`services.py` (единственное место, где живёт `emit()`):

```python
class NoteCreated(DomainEvent):
    topic: ClassVar[str] = "note.created"

    note_id: UUID
    title: str
```

- `topic` — `<сущность>.<что случилось>` в прошедшем времени, стабилен: он
  живёт в очереди дольше выкатки;
- событие — **факт**, а не команда: `note.created`, не `send.email`;
- поля JSON-сериализуемы (`emit()` делает `model_dump(mode="json")`) и несут
  всё нужное потребителю, чтобы тот не ходил к владельцу таблицы;
- `emit()` синхронный, без единого `await` — это только `session.add()`.

Событие на каждую операцию заводить не нужно: PATCH и DELETE порождают событие
только если снаружи на них кто-то реагирует.

### Подписчик — чужой факт

`subscribers.py` создаётся, только если модуль слушает **чужие** события.
На собственное событие модуль не подписывается: эффект, нужный сразу после
записи, делается прямым вызовом в том же сервисе.

**Класс чужого события не импортируется** — контракт import-linter
«Business modules never import each other» ломается и на `events.py` соседа.
Контракт между модулями — топик, а не класс: объяви у себя своё событие с тем
же `topic` и только нужными полями, лишнее pydantic отбросит.

```python
class FileArrived(DomainEvent):
    topic: ClassVar[str] = "file.confirmed"

    file_id: UUID
    key: str


@subscribe(FileArrived)
async def attach_file(event: FileArrived, _session: AsyncSession) -> None:
    ...
```

- `@subscribe(Event)` обязателен: функция в `Module.subscribers` без него
  роняет процесс на старте;
- сигнатура всегда `(event, session)`; сессия не нужна — назови `_session`;
- **подписчик обязан быть идемпотентным**: доставка at-least-once, и
  исключение откатывает транзакцию вместе с отметкой `processed_messages`,
  после чего сообщение приезжает снова.

### TaskIQ — наша фоновая работа

```python
@schedule(interval=timedelta(hours=1))
async def purge_notes() -> int:
    return await purge_old_notes(session_factory=db_session.session_factory)
```

- `@schedule(cron=...)` или `@schedule(interval=...)`; расписание берётся из
  настроек модуля, а не зашивается числом;
- фабрика сессий читается из модуля (`db_session.session_factory`), а не
  импортируется по имени: тесты подменяют глобаль ядра;
- задача не падает целиком из-за одного элемента: отказ по элементу — запись в
  лог и следующий элемент;
- клиентов внешних сервисов задача создаёт сама: `lifespan` модуля исполняет
  только uvicorn, воркер его не поднимает.

Образец с обоими видами расписания — `src/app/modules/storage/tasks.py`.

### Консьюмер RabbitMQ — чужое сообщение

`consumers.py` плюс `TopologyDecl` и `ConsumerDecl` в манифесте. Формат
сообщения — чужой контракт, менять его нельзя. Поля `dead_letter`,
`retry_ttl_ms`, `prefetch`, `requires_idempotency` с объяснением каждого
умолчания — в `src/app/kernel/registry.py`; читай их там, а не угадывай.
Защита от повтора — `run_once` по `processed_messages`
(`src/app/platform/idempotency.py`), в одной транзакции с самим эффектом.

## Шаг 3. Впиши в манифест

Всё, кроме `after_commit`, требует строки в `module.py`:

| Механизм | Поле `Module` |
| --- | --- |
| подписчик | `subscribers=(...)` — функции с `@subscribe` |
| задача TaskIQ | `tasks=(...)` — корутины с `@schedule` |
| консьюмер | `consumers=(...)` + `topology=(...)` |

Функция в `subscribers` или `tasks` без декоратора — ошибка конфигурации,
процесс не поднимется.

## Чего делать нельзя

- **`kiq()` из HTTP-ручки.** Это обращение к брокеру, а внутри транзакции
  внешнего I/O нет. Работа, которую нельзя потерять, ставится строкой в таблице
  (статус, outbox), а не задачей в брокер.
- **Фоновая работа в процессе uvicorn.** Ни консьюмер, ни шедулер, ни релей там
  не поднимаются: такая работа умирает при перекатке и размножается вместе с
  числом воркеров uvicorn — периодическая задача начинает выполняться N раз.
  Всё фоновое живёт только в `worker.py`.
- **Внешний вызов внутри открытой транзакции.** Порядок всегда один: короткая
  читающая сессия → закрыли → внешний вызов → короткая пишущая транзакция.
