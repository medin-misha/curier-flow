# Модуль `storage`

Загрузка и выдача файлов **без прохождения содержимого через backend**.
Приложение хранит метаданные, выдаёт подписанные ссылки и проверяет результат;
байты ходят между клиентом и объектным хранилищем напрямую.

| Ручка                       | Что делает                                       |
| --------------------------- | ------------------------------------------------ |
| `POST /files/upload-url`    | заводит строку `pending`, отдаёт presigned PUT   |
| `POST /files/{id}/confirm`  | HEAD объекта, сверка, `ready` + `FileConfirmed`  |
| `GET /files/{id}`           | метаданные и presigned GET (только у `ready`)    |
| `GET /files`                | keyset-страница, без файлов в `deleting`         |
| `DELETE /files/{id}`        | помечает `deleting`, объект удалит задача        |

## Файлы через backend не проксируются

Ни `UploadFile`, ни `StreamingResponse`, ни «маленький файл можно и через нас».
Проксирование стоит воркера uvicorn на всё время передачи: сотня параллельных
загрузок по минуте — это сотня занятых воркеров и очередь из отвалившихся по
таймауту обратного прокси запросов. Плюс лимит `client_max_body_size` у прокси,
плюс память процесса под тело. Хранилище умеет то же самое, стоит дешевле и
масштабируется без нас.

Практический вывод: `fastapi.responses.FileResponse` в этом модуле не нужен
вовсе. Схема ответа с таким же именем — это метаданные, а не содержимое.

## Жизненный цикл файла

```
                POST /files/upload-url
                        │  (транзакция закоммичена ДО выдачи ссылки)
                        ▼
                    ┌────────┐   PUT по ссылке   ┌──────────────┐
                    │pending │ ────────────────▶ │ объект в S3  │
                    └────────┘                   └──────────────┘
                     │      │
   POST .../confirm  │      │  клиент пропал, TTL истёк
   HEAD + сверка     │      │  (sweep_orphaned_uploads)
                     ▼      ▼
                 ┌───────┐  ┌──────────┐
                 │ ready │  │ deleting │◀── DELETE /files/{id}
                 └───────┘  └──────────┘
                     │            │  delete_marked_files:
                     └────────────┘  сначала объект, потом строка → строки нет
```

Кто меняет статус:

- `pending` ставит `create_upload` — единственное место, где строка рождается;
- `ready` ставит `confirm_upload` в одной транзакции с `emit(FileConfirmed)`;
- `deleting` ставит `mark_for_deletion` (ручка DELETE) или сборщик сирот,
  когда `pending` пережила `STORAGE_ORPHAN_TTL`;
- строку удаляет только `delete_marked_files`, и только после того, как объект
  в хранилище удалён.

Из `deleting` возврата нет. `confirm` и `GET` на таком файле отвечают **404**:
ответив на DELETE, сервис пообещал, что файла больше нет, и остальные ручки
обязаны отвечать так же. Воскрешение строки дало бы `ready` без содержимого —
задача уже удаляет объект.

## Внешний I/O вне транзакции — главное правило модуля

Границы транзакций держит `services.py`, а не зависимость `get_uow`: каждая
операция модуля сочетает базу и хранилище. Порядок всегда один:

```
короткая читающая сессия → закрыли → поход в хранилище → короткая пишущая транзакция
```

HEAD и DELETE идут по сети. Внутри открытой транзакции они держали бы
соединение из пула и блокировки строк всё время ответа хранилища — а лежащее
хранилище отвечает таймаутом, то есть десятками секунд. Подпись ссылки сети не
касается, но вынесена наружу транзакции тоже: одно исключение из правила
скопируют в соседний модуль вместе с сетевым вызовом.

Сторожит это тест `test_s3_calls_never_happen_inside_a_transaction`: он
подменяет методы `ObjectStorage` обёрткой, которая падает, если в момент
вызова у любой сессии открыта транзакция. Обёртка включена во всех тестах
модуля, поэтому вернуть S3 внутрь транзакции незаметно не получится.

`kiq()` из ручки DELETE не вызывается по той же причине: постановка задачи —
это обращение к брокеру, и внутри транзакции ему не место. Поэтому удаление
делает периодическая задача, а не отложенная.

## Ловушка presigned-ссылки: адрес хранилища

Подпись SigV4 накрывает заголовок `Host`. Ссылка, подписанная на
`http://minio:9000` (так хранилище видно изнутри compose), в браузере придёт с
`Host: localhost:9000` и получит `SignatureDoesNotMatch`. **Подменить хост в
готовой ссылке нельзя** — подпись перестанет сходиться.

Поэтому в настройках два адреса:

- `S3_ENDPOINT_URL` — куда ходит приложение (`http://minio:9000` в compose);
- `S3_PUBLIC_ENDPOINT_URL` — куда придёт клиент (`http://localhost:9000`);
  пусто — значит совпадает с первым.

`platform/s3.py` создаёт под публичный адрес второй клиент и подписывает
ссылки им. Запросов он не делает, соединений не открывает.

В проде это адрес CDN или публичный домен бакета. Если ссылки «не открываются
у клиента, но работают с сервера» — проверять надо именно эту переменную.

## Ключ объекта

`uploads/ГГГГ/ММ/ДД/<uuid7>` — генерирует сервер, в схеме запроса ключа нет.
Клиент, задающий ключ, перезаписал бы чужой объект.

- Дата в префиксе разбивает бакет на каталоги по дням: один каталог на весь
  сервис не посмотреть консолью и не накрыть правилом жизненного цикла.
- Оригинальное имя в ключ не подставляется: в нём бывают пробелы, юникод и
  `../`. Оно хранится колонкой и попадает в `Content-Disposition` ссылки на
  скачивание.
- Расширения в ключе нет: тип содержимого хранится колонкой, а имя файла при
  скачивании задаёт та же `Content-Disposition`.

## Что клиент заявляет и что сервер проверяет

`POST /files/upload-url` — клиент присылает `original_name`, `content_type` и
заявленный `size`. Проверка по лимитам (`STORAGE_ALLOWED_CONTENT_TYPES`,
`STORAGE_MAX_FILE_SIZE`) происходит **до** создания строки: отказ по лимиту
после того, как клиент залил сто мегабайт, — плохой сервис. Тип вшивается в
подпись, поэтому PUT с другим `Content-Type` хранилище не примет.

`POST /files/{id}/confirm` — клиент присылает ETag, который вернуло хранилище.
Сервер делает `head_object` и сверяет:

| Проверка                       | Не сошлось                     |
| ------------------------------ | ------------------------------ |
| объект существует              | 404, строка остаётся `pending` |
| размер ≤ лимита                | объект удаляется, 422          |
| размер равен заявленному       | объект удаляется, 422          |
| `Content-Type` равен заявленному | объект удаляется, 422        |
| ETag равен присланному         | объект удаляется, 422          |

После 422 строка остаётся `pending` намеренно: подписанная ссылка ещё жива, и
клиент вправе перезалить файл правильно. Не заберёт — уберёт сборщик сирот.

Повторный `confirm` готового файла возвращает 200 и ту же строку: это обычный
ретрай после обрыва, а не ошибка. Объект при этом **не перепроверяется** — иначе
ретрай с неудачным ETag удалил бы содержимое уже принятого файла. Второго
события повтор не порождает.

Сверка `Content-Type` держится на том, что тип вшит в подпись: хранилище не
приняло бы PUT с другим заголовком, и расхождение означает, что объект под этим
ключом появился не тем путём, которым его ждали. Если модуль когда-нибудь
начнёт подписывать ссылки без `content_type`, эту сверку надо снимать первой:
S3 в таком случае проставит `application/octet-stream` сам, и валидная загрузка
будет отвергаться.

## Событие

`FileConfirmed` (топик `file.confirmed`) пишется в outbox той же транзакцией,
что и смена статуса на `ready`: либо файл готов и событие уехало, либо ни того,
ни другого. Тест `test_confirmation_and_the_event_share_one_transaction`
доказывает это откатом — падение на коммите не оставляет ни статуса, ни строки
в outbox.

Событие несёт `bucket` и `key`: потребитель (превью, антивирус, индексатор)
должен уметь взять объект, не обращаясь к владельцу таблицы. Подписчиков в
этом модуле нет — модуль не подписывается на собственные события.

## Задачи

| Задача                            | Расписание                    | Что делает                          |
| --------------------------------- | ----------------------------- | ----------------------------------- |
| `storage.sweep_orphaned_uploads`  | `STORAGE_ORPHAN_SWEEP_CRON`   | `pending` старше TTL → объект и строка |
| `storage.delete_marked_files`     | `STORAGE_DELETION_INTERVAL`   | `deleting` → объект и строка        |

Инварианты, которые нельзя нарушать при правке:

- **Сначала объект, потом строка.** В обратном порядке сбой между шагами теряет
  объект навсегда: ключ хранится только в строке.
- Сборщик сирот сперва помечает строки `deleting` отдельной транзакцией
  (`UPDATE ... WHERE id IN (SELECT ... FOR UPDATE SKIP LOCKED)`), и только
  потом идёт удалять. Пометка отбирает строку у гонки: опоздавшее
  подтверждение уже не сделает готовым файл, объект которого вот-вот удалят.
- Отказ по одному файлу не прекращает проход: строка остаётся `deleting` и
  попадёт в следующий.
- Задачи создают клиент хранилища на каждый запуск: `lifespan` модуля
  поднимает только приложение FastAPI, воркер его не исполняет.

## Индексы

- `ix_files_keyset` — `(created_at DESC, id DESC)`, без него keyset-пагинация
  вырождается в сортировку таблицы;
- `ix_files_status_created_at` — выборка обеих задач;
- `uq_files_bucket_key` — две строки на один объект означают потерянный объект:
  уборка одной удалила бы объект из-под второй.

Индекса по `owner_id` нет: колонка заполнится, когда появится аутентификация, и
вместе с фильтром «мои файлы» понадобится `(owner_id, created_at DESC, id DESC)`.
Раньше он был бы мёртвым грузом.

## Команды

```bash
uv run pytest tests/test_storage.py -v      # тесты модуля (нужен docker)
uv run alembic upgrade head                 # таблица files
uv run alembic check                        # схема совпадает с моделями

# Полный цикл руками (стек поднят через make up):
curl -s localhost:8000/files/upload-url -H 'content-type: application/json' \
  -d '{"original_name":"a.png","content_type":"image/png","size":4}'
curl -i -X PUT "<upload_url>" -H 'content-type: image/png' --data-binary @a.png
curl -s -X POST localhost:8000/files/<id>/confirm -H 'content-type: application/json' \
  -d '{"etag":"<etag из заголовка ответа PUT>"}'
curl -s localhost:8000/files/<id>           # download_url открывается в браузере
```

## Если правишь модуль

- Новый лимит → поле в `StorageSettings`, переменная в `.env.example`,
  проверка в `_check_declared` (по заявке) и в `_mismatch` (по факту).
- Новая ручка, которой нужно хранилище, — тот же порядок: чтение, закрытие
  сессии, S3, пишущая транзакция. Тест-сторож не даст сделать иначе.
- Не добавляй `kiq()` в HTTP-ручки: работа, которую нельзя потерять, ставится
  через статус в таблице, а не через брокер внутри транзакции.
- `owner_id` не должен появиться в схеме запроса: он приходит из `actor_id` и
  передаётся только через `**overrides` в `CRUD.create`.
