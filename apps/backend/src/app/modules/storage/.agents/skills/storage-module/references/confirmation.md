## Что клиент заявляет и что сервер проверяет

`POST /files/upload-url` — клиент присылает `original_name`, `content_type` и
заявленный `size`. Проверка по лимитам (`STORAGE_ALLOWED_CONTENT_TYPES`,
`STORAGE_MAX_FILE_SIZE`) происходит **до** создания строки: отказ по лимиту
после того, как клиент залил сто мегабайт, — плохой сервис. Тип вшивается в
подпись, поэтому PUT с другим `Content-Type` хранилище не примет.

`POST /files/{id}/confirm` — клиент присылает ETag, который вернуло хранилище.
Сервер делает `head_object` и сверяет:

| Проверка                       | Не сошлось                     |
| ------------------------------ | ------------------------------ |
| объект существует              | 404, строка остаётся `pending` |
| размер ≤ лимита                | объект удаляется, 422          |
| размер равен заявленному       | объект удаляется, 422          |
| `Content-Type` равен заявленному | объект удаляется, 422        |
| ETag равен присланному         | объект удаляется, 422          |

После 422 строка остаётся `pending` намеренно: подписанная ссылка ещё жива, и
клиент вправе перезалить файл правильно. Не заберёт — уберёт сборщик сирот.

Повторный `confirm` готового файла возвращает 200 и ту же строку: это обычный
ретрай после обрыва, а не ошибка. Объект при этом **не перепроверяется** — иначе
ретрай с неудачным ETag удалил бы содержимое уже принятого файла. Второго
события повтор не порождает.

Сверка `Content-Type` держится на том, что тип вшит в подпись: хранилище не
приняло бы PUT с другим заголовком, и расхождение означает, что объект под этим
ключом появился не тем путём, которым его ждали. Если модуль когда-нибудь
начнёт подписывать ссылки без `content_type`, эту сверку надо снимать первой:
S3 в таком случае проставит `application/octet-stream` сам, и валидная загрузка
будет отвергаться.
