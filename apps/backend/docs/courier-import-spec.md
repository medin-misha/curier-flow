# Импорт курьеров из старой базы

## Объём и результат

Источник — `database_export.xlsx`, только лист `Users`, все непустые записи
в исходном порядке. На момент подготовки: 827 записей, а не ровно 800.
Другие листы, договоры, транспорт и документы не импортируются.
Схема PostgreSQL не меняется.

Процесс состоит из трёх этапов:

1. `scripts/export_couriers.py`: Excel → `couriers.json` без потери исходных
   столбцов, с номером строки и старым ID.
2. `scripts/convert_couriers.py`: исходный JSON → `couriers_import.json`,
   соответствующий входному контракту API; отдельный `couriers_report.json`
   описывает ошибки, предупреждения и повторы.
3. `scripts/import_couriers.py`: проверка или запись через защищённый
   `POST /import-courier`; результат сохраняется в локальном JSON.

Файлы с исходными и преобразованными персональными данными хранятся в
`tmp/courier-import/`, исключённом из Git. Повторная конвертация воспроизводима;
времена проверки/импорта не считаются исходными данными.

## Сопоставление полей

| Users | Новая модель | Правило |
| --- | --- | --- |
| name | full_name | Удалить пробелы по краям |
| email | email | Текущая нормализация CREATE: strip + lower |
| phone | phone | Текущая нормализация CREATE; опциональный явно заданный префикс для девяти цифр |
| birth_date | date_of_birth | ISO-дата; отсутствие/будущая дата — ошибка |
| city | city | Удалить пробелы по краям; не исправлять названия догадками |
| address | address | Удалить пробелы по краям |
| citizenship | citizenship | Удалить пробелы по краям |
| invoice | bank_account | Сохранить текст после strip; сомнительный формат отметить |
| telegram, whatsapp | contact_platform, contact | Telegram имеет приоритет; WhatsApp сохраняется без изменений; второй контакт остаётся в исходном JSON и отмечается в отчёте |
| how_found_it | source | Только если укладывается в 64 символа; иначе null и предупреждение, полный текст остаётся в исходном JSON |
| consent | consent_to_processing | Только явные true/false; дату старого согласия не выдумывать |
| created_at | created_at | Сохранить aware timestamp старой регистрации |
| work_in | platform_accounts[].platform | bolt/Bolt Food → bolt_food; foodora → foodora; wolt → wolt; допускается несколько платформ |
| status | platform_accounts[].status | Один старый статус назначить всем явно распознанным платформам |
| id | legacy_id | Только связь с источником; новый UUID создаёт система |
| desired_transport | — | Сохранить только в исходном JSON; это пожелание, а не объект автопарка |

`bolt?` и `foodora?` распознаются только с `--accept-question-platforms`,
с предупреждением на каждую строку. Неизвестные платформы (в том числе
`Prague`) — ошибка. Суффикс `перевод` допустим для `bolt перевод`, отмечается
предупреждением. Текстовые разделители платформ: запятая, `/`, пробельные
символы и литеральное `\n` из старого экспорта.

Префикс `+420` не добавляется API автоматически. Конвертер делает это только
при `--local-phone-prefix +420` для ровно девяти цифр и отмечает исправление.
Международный префикс `00` преобразуется в `+` с предупреждением. Другие
невалидные номера и обязательные поля не заменяются фиктивными значениями.

При согласии `consent_at` означает время фиксации согласия в новой системе
(время импорта), а не неизвестное время старого согласия. `created_at`
сохраняет старую дату создания; `updated_at` — время импорта.

## Статусы

Регистр и крайние пробелы не влияют на сопоставление.

| Старый статус | Новый статус |
| --- | --- |
| Pending | pending |
| Processing | active |
| In activation | active |
| Active | active |
| Inoperative | inactive |

Пустые и неизвестные статусы — ошибки. `problem` конвертер не назначает.

## JSON и ошибки преобразования

Исходный файл: `schema_version: 1`, `sheet: "Users"`, `couriers` — список
`{source_row, legacy_id, values}`. `values` содержит исходные столбцы.

Файл для API: `schema_version: 1`, `couriers` — список
`{source_row, legacy_id, courier}`. `courier` содержит scalar-поля и
`platform_accounts: [{platform, status}]`; загрузки файлов отсутствуют.
API допускает от 1 до 1000 записей; source_row и legacy_id уникальны.

Конвертер сохраняет все валидные строки, включая natural-key повторы; не
объединяет поля из разных записей. Отчёт содержит число исходных, готовых и
отклонённых строк, проблемы по строкам, нормализации и совпадения email/phone.
Если есть отклонённые строки, конвертер записывает артефакты и завершает работу
с кодом 2. Пропуск не должен выглядеть как полный успешный перенос.

## API и идемпотентность

`POST /import-courier?dry_run=true` выполняет проверку без записи. По умолчанию
`dry_run=true`. Для записи клиент обязан явно передать `dry_run=false`.
Требуется Admin access JWT; `Idempotency-Key` не требуется, защита основана
на тех же natural keys, что у `POST /courier`.

- Совпадений нет: создать Courier и platform accounts с переданными статусами.
- Email **или** phone совпал с одним Courier: `existing`, вернуть ID;
  не обновлять и не дополнять Courier, аккаунты, документы и статусы.
- Email одного Courier и phone другого: `conflict`, `reason=identity-split`;
  не объединять и не писать эту строку.
- Параллельный INSERT: `ON CONFLICT DO NOTHING`, вернуть победителя;
  если identity исчезла/изменилась — `identity-conflict`.
- Обработка идёт в порядке входного файла; первая успешно созданная запись
  определяет сохранённые данные для последующих повторов.
- Dry run моделирует также повторы и split внутри самой пачки. Для новых
  строк возвращается `would_create`, без фиктивного persistent ID.
- Ответ `200`: `dry_run`, счётчики и результат каждой строки с source_row,
  legacy_id, outcome, courier_id и reason. Счётчики dry run — прогноз:
  состояние БД может измениться до записи.

Запись — одна function-scoped UoW на запрос. Доменные identity-conflicts
попадают в отчёт; остальные валидные записи коммитятся. Неожиданная ошибка
откатывает весь запрос. Невалидный JSON/контракт даёт 422 и не пишет ничего.
Повтор с новым запросом сообщает `existing` вместо прежнего `created`.

Импорт не создаёт `CourierRegistered`: исторический перенос не запускает
уведомления о новых заявках. Для новых Courier создаётся `CourierProfileChanged`
в той же транзакции для синхронизации контактов. Повторы не создают событий.

## Запуск

Из `apps/backend/`, после установки зависимостей:

```bash
.venv/bin/python -m scripts.export_couriers ../../database_export.xlsx \
  --output ../../tmp/courier-import/couriers.json
.venv/bin/python -m scripts.convert_couriers ../../tmp/courier-import/couriers.json \
  --output ../../tmp/courier-import/couriers_import.json \
  --report ../../tmp/courier-import/couriers_report.json \
  --local-phone-prefix +420 --accept-question-platforms
.venv/bin/python -m scripts.import_couriers ../../tmp/courier-import/couriers_import.json \
  --url https://backend.localhost --token-file /path/to/admin-token \
  --output ../../tmp/courier-import/import-preview.json
```

Клиент по умолчанию делает dry run. Для записи нужен `--apply` и проверка тем
же клиентом без конфликтов; `--allow-conflicts` разрешает явно выбранный
частичный импорт с отчётом. HTTPS проверяется; локальный CA задаётся `--ca-file`.
Токен читается из файла, не выводится и не передаётся в командной строке.

Перед фактической загрузкой проверить отчёт преобразования и определить
действия для отклонённых строк. Для полного переноса исправить источник и
повторить преобразование; новые значения обязательных полей не выдумываются.

## Проверки при реализации

- XLSX: точный лист, inline/shared strings, пустые строки, bool/numeric/date,
  отсутствие потери столбцов и привязка к строке; опасные/битые структуры
  отклоняются.
- Преобразование: все пять статусов, несколько платформ, явные исправления
  телефонов, некорректные даты/платформы/consent, ограничение длины, отчёт дублей.
- API на PostgreSQL: Admin auth, dry run без записи/outbox, сохранение статусов
  и исторической даты, повторы, identity-split, split внутри пачки,
  параллельные импорты, откат при ошибке и отсутствие registration events.
- Проверить совместимость прежнего POST и OpenAPI, `make check`, `make test`,
  `alembic check`. Управлять контейнерами только из `infra/`.

## Выполненная загрузка, 2026-10-06

Все 827 строк `Users` сохранены в исходном JSON. В API отправлены 814
валидных строк: создано 782 курьера и 787 аккаунтов платформ; 32 строки
обработаны как повторы. Из них две строки совпали с одним ранее существовавшим
курьером, остальные 30 — повторы внутри файла. Конфликтов identity нет.
Ранее существовавший aggregate проверен до/после импорта и не изменился.
Итог БД: 783 курьера, 788 аккаунтов платформ.

13 отклонённых строк оставлены в отчёте по решению пользователя: семь с
невалидным телефоном, четыре с будущей датой рождения, две с `Prague` вместо
платформы и отсутствующей датой рождения. WhatsApp сохранён без изменений;
`+420` применён к локальным телефонам, `bolt?`/`foodora?` преобразованы с
предупреждениями. Все scalar-поля и аккаунты созданных курьеров сверены с JSON.

Артефакты находятся в `tmp/courier-import/` от корня репозитория:
`couriers.json`, `couriers_import.json`, `couriers_report.json`,
`import-result.json` и `verification.json`.

Пройдены 46 проверок импорта, OpenAPI и архитектуры, `make check` и Alembic
check. Полный `make test` не завершён из-за окружения: проверка готовности
тестового RabbitMQ завершается таймаутом, старый MinIO image из Quay
недоступен (`401 Unauthorized`). Приложения пересобраны через
`make -C infra reboot-apps`, импорт выполнен через HTTPS API с Admin JWT.
