# ADR 0002. Keyset-пагинация вместо OFFSET

**Статус:** принято · **Дата:** 2026-08-10

## Контекст

Списки нужно листать. Привычный способ — `LIMIT ... OFFSET ...` с параметрами
`page` и `per_page`. У него два дефекта, и второй серьёзнее первого.

**Деградация.** `OFFSET n` заставляет Postgres прочитать и отбросить `n` строк.
Страница 1 стоит миллисекунды, страница 10 000 — секунды. Плата растёт линейно
и приходится ровно на тех, кто листает глубоко: экспортёров, ботов, интеграции.

**Пропуски и дубли.** Между запросом страницы 1 и страницы 2 кто-то вставил
строку в начало списка. Строка, бывшая последней на первой странице, съезжает
на вторую — клиент видит её дважды. При удалении — наоборот, строка теряется
и не попадёт ни на одну страницу. На ленте, отсортированной по времени создания
и пополняемой сверху, это происходит постоянно.

## Решение

Курсор по стабильному ключу `(created_at, id)`, сортировка
`ORDER BY created_at DESC, id DESC`, следующая страница —
`WHERE (created_at, id) < (:created_at, :id)`.

`id` входит в ключ обязательно: `created_at` не уникален, и без второго
компонента строки с одинаковой меткой времени теряются на границе страниц.
Кортежное сравнение, а не `created_at < :ts OR (created_at = :ts AND id < :id)`:
одно выражение, которое планировщик умеет свести к поиску по индексу.

Курсор непрозрачен для клиента — base64url от `ISO-8601|UUID`. Метка времени
сохраняется с микросекундами и смещением: округление хотя бы до секунды ломает
keyset. Любой мусор в курсоре — 422, а не 500.

Ответ — `Page[T]` с `items` и `next_cursor`; `next_cursor is None` означает, что
данные кончились. Запрашивается на одну строку больше, чем нужно: её наличие и
есть признак следующей страницы.

## Последствия

- Стоимость страницы не зависит от её номера.
- Вставки и удаления в уже пролистанной части списка на выдачу не влияют.
- **Каждой листаемой таблице нужен индекс**
  `(created_at DESC, id DESC)` — иначе Postgres сортирует таблицу целиком, и
  keyset оказывается медленнее OFFSET. Индекс объявляется после класса модели:
  внутри тела класса колонок ещё нет, а строка вместо выражения потеряла бы
  направление сортировки.
- **Нет общего числа страниц и нельзя прыгнуть на страницу N.** Интерфейс
  «1 2 3 … 57» на keyset не строится. Нужен «показать ещё» или бесконечная
  лента.
- `COUNT(*)` для «всего записей» отдельно не делается: он стоит полного прохода
  по таблице, то есть ровно того, от чего мы ушли.
- Порядок сортировки фиксирован. Сортировка по другому полю потребует своего
  ключа курсора и своего индекса.

## Альтернативы

**`LIMIT/OFFSET`.** Отвергнут по причинам выше. Допустим только для заведомо
коротких справочников, но заводить два механизма пагинации в шаблоне — значит
гарантировать, что выберут привычный.

**Курсор по одному `id` (UUIDv7).** UUIDv7 монотонен по времени, поэтому
теоретически хватает его одного. Отвергнуто: порядок по `id` не совпадает с
порядком по `created_at`, который проставляет сервер БД, и на строках,
вставленных не приложением (импорт, ручной `INSERT`), выдача разъехалась бы с
сортировкой.

**Смещение по `created_at` без `id`.** Простой курсор, но теряет строки с
совпадающей меткой времени. При пакетной вставке метки совпадают массово.
