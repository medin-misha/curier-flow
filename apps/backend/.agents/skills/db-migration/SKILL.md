# Изменение схемы

Схема меняется **только миграцией**. Инварианты файла ревизии — в
`.agents/rules/migrations.md` от `apps/backend/`; прочитай его явно
до изменения модели или ревизии. Здесь — порядок действий, который нельзя
переставлять.

Рабочий каталог для относительных путей и команд — `apps/backend/`; задавай его
инструменту явно независимо от рабочего каталога сессии.

## 1. Правь модель

ORM-модель в `src/app/modules/<name>/models/`. Пагинируемой таблице нужен
составной индекс, объявленный **после класса** (внутри тела колонок ещё нет, и
направление сортировки строкой не задать):

```python
Index("ix_notes_keyset", Note.created_at.desc(), Note.id.desc())
```

Без него keyset-пагинация вырождается в сортировку всей таблицы.

## 2. Подними базу и сгенерируй ревизию

Autogenerate ходит в базу, поэтому Postgres должен быть поднят и накатан.
Окружение стека и применение существующей цепочки принадлежат `infra/`, а
генерация новой ревизии остаётся локальным инструментом разработки. Перед
генерацией `DATABASE_DSN` хостового окружения должен указывать на поднятый
Postgres из `infra/`:

```bash
make -C ../../infra up-infra # запуск контейнеров всегда идёт через infra/
make -C ../../infra migrate  # накатить существующую цепочку в окружении стека
make revision m="add notes"
```

Имя ревизии — по дате и смыслу, как у существующих
(`20260809_2034_files_table.py`).

## 3. Отформатируй — сразу

Autogenerate пишет в своём стиле (одинарные кавычки, длинные строки), и
`make check` на этом падает:

```bash
uv run ruff format alembic/versions/<новый файл>.py
```

## 4. Прочитай сгенерированный файл

Это не формальность, а самый важный шаг: autogenerate не видит переименований.

- имя таблицы, типы колонок и `nullable` — те, что задумывались;
- **переименование колонки** превращено в «удалить + создать» — с потерей
  данных. Такие правки пишутся руками (`op.alter_column(..., new_column_name=...)`);
- keyset-индекс на месте и **направление сортировки сохранено**:

  ```python
  op.create_index(
      "ix_notes_keyset",
      "notes",
      [sa.literal_column("created_at DESC"), sa.literal_column("id DESC")],
      unique=False,
  )
  ```

  Индекс без `DESC` бесполезен для `ORDER BY created_at DESC, id DESC`;
- в ревизию не попали таблицы из `tests/models.py` — это полигон тестов ядра,
  он создаётся отдельным `create_all` по явному списку;
- `downgrade()` действительно возвращает базу к прежнему состоянию. Это
  проверяется локальным циклом отката и повторного наката изменённой ревизии;
  пустой или неполный `downgrade()` — дефект миграции, а не мелочь.

## 5. Накати и проверь

```bash
make -C ../../infra migrate
uv run alembic check    # «No new upgrade operations detected»
```

`alembic check` ловит расхождение моделей и миграций, из-за которого `make test`
упал бы на создании схемы: `tests/conftest.py` строит схему прогона именно
миграциями.

## 6. Проверь откат

Выполняй цикл на отдельной локальной базе без ценных данных: откат может удалять
колонки и таблицы. После шага 5 база находится на `head`, поэтому `-1` проверяет
именно изменённую ревизию:

```bash
uv run alembic downgrade -1
uv run alembic upgrade head
uv run alembic check
```

## Перед коммитом

Файл миграции и изменённая модель идут **одним** коммитом: разъехавшиеся модель
и миграция — это красный `alembic check` у следующего, кто сделает pull. Дальше
— скилл `pre-commit`.
