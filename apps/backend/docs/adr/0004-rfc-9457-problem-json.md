# ADR 0004. Все ошибки — RFC 9457 `application/problem+json`

**Статус:** принято · **Дата:** 2026-08-10

## Контекст

По умолчанию FastAPI отдаёт ошибки в трёх разных форматах:

- `{"detail": "Not Found"}` — от `HTTPException` и от маршрутизатора;
- `{"detail": [{"loc": [...], "msg": ..., "type": ..., "input": ..., "url": ...}]}`
  — от ошибки валидации;
- HTML-трейсбек или пустой 500 — от необработанного исключения.

Клиенту приходится разбирать три схемы, ни одна из которых не несёт машинного
кода ошибки. `detail` — то строка, то список, и отличить «не найдено» от
«не разрешено» можно только по HTTP-статусу, которого не хватает: у 409 бывает
десяток разных причин.

Отдельная проблема — `input` в отчёте pydantic: он возвращает клиенту его же
данные, включая пароли, и попадает в логи прокси.

## Решение

Единственный формат ответа об ошибке — RFC 9457 (бывший 7807),
`Content-Type: application/problem+json`:

```json
{
  "type": "https://errors.local/validation-failed",
  "title": "Validation Failed",
  "status": 422,
  "detail": "Content type is not allowed",
  "instance": "/files/upload-url",
  "request_id": "01J...",
  "content_type": "image/gif",
  "allowed": ["application/pdf", "image/jpeg", "image/png"]
}
```

- бизнес-код поднимает наследника `AppError` из `app.kernel.errors`; у класса
  есть `code`, `status` и `title`, а `detail` и произвольные дополнительные
  члены задаются на месте;
- `HTTPException` запрещён линтером во всём проекте (все три написания). Слой
  `api` — единственное место, где ошибка превращается в HTTP-ответ;
- к одному формату приводятся **все** источники: доменная ошибка, ошибка
  валидации FastAPI, ответ самого фреймворка (404 на путь, 405 на метод) и
  необработанное исключение;
- `request_id` есть в каждом ответе и в каждой записи лога;
- дополнительные члены не вправе перезаписать стандартные (`type`, `title`,
  `status`, `detail`, `instance`, `request_id`);
- из отчёта валидации наружу уходят только `loc`, `msg` и `type`: `input`
  вернул бы клиенту его данные, `url` ссылается на документацию pydantic, а не
  на наш API;
- необработанное исключение отдаёт пустой 500 без типа и текста: и то и другое
  выдаёт устройство сервиса и клиенту не помогает. Связать ответ с трейсбеком
  можно по `request_id`.

`type` строится как `{ERRORS_BASE_URL}/{code}`: в RFC 9457 это ссылка на
описание проблемы, и у сервиса с публичной документацией она указывает на
реальную страницу.

## Последствия

- Клиент разбирает ошибки по одной схеме и ветвится по `type`/машинному коду,
  а не по тексту `detail`.
- Дополнительные члены — штатный способ передать подробности («какие поля
  непатчабельны», «какие типы разрешены»), не изобретая `errors[]`.
- Стандартный обработчик FastAPI переопределён целиком, поэтому чужие рецепты
  из интернета, добавляющие `HTTPException`, в этом проекте не работают — и это
  ловит линтер, а не ревью.
- `AppError` не знает про HTTP: тот же сервис вызывается из воркера и из
  скрипта, где статус-кода нет.
- Стоимость: собственная иерархия ошибок и обязанность заводить в ней новый
  класс вместо «просто верну 418».

## Альтернативы

**Оставить `{"detail": ...}` как есть.** Бесплатно, но клиент получает три
схемы и ни одного машинного кода.

**Свой формат (`{"error": {"code": ..., "message": ...}}`).** Ничем не хуже по
существу, но требует объяснять его каждому потребителю. RFC 9457 — стандарт с
зарегистрированным media type, его понимают генераторы клиентов и шлюзы.

**JSON:API errors.** Мощнее, но тянет за собой весь JSON:API с его
`data/attributes/relationships`; для сервиса, который не отдаёт JSON:API,
это чужая схема ради одного раздела.
