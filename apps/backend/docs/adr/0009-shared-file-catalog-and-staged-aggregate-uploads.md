# ADR 0009. Общий каталог файлов и staging для агрегатных загрузок

**Статус:** принято · **Дата:** 2026-08-22

## Контекст

Модуль Courier должен одним `POST /courier` принять multipart с документами и
создать Courier, аккаунты платформ, документы и файлы. При этом в backend уже
действуют три ограничения:

1. бизнес-модули не импортируют друг друга;
2. S3, HTTP и брокер не вызываются внутри открытой DB-транзакции;
3. обычный файловый сценарий передаёт байты напрямую между клиентом и S3:
   `POST /files/upload-url` → PUT в S3 → `POST /files/{id}/confirm`.

Сейчас ORM-модель `File`, `FileStatus` и событие `FileConfirmed` принадлежат
бизнес-модулю `storage`. Прямой импорт этих объектов из Courier нарушил бы
границу модулей. Вызов HTTP API `storage` или обмен событием не решает задачу:
строки Courier и File тогда создаются разными транзакциями и один успешный
запрос не может гарантировать целостность агрегата.

PostgreSQL и S3 не поддерживают общую транзакцию. Если сначала загрузить
объект, а затем упасть до записи File, ключ объекта потеряется. Если держать
DB-транзакцию открытой во время upload, соединение и блокировки останутся
заняты на всё время сетевого вызова, но атомарности с S3 всё равно не
появится.

## Решение

### Общий DB-каталог

`File`, `FileStatus`, контракт события `FileConfirmed` и операции, которым
нужна только БД, переносятся в `app.platform.files`. Это общая техническая
подсистема нижнего слоя, которую вправе использовать любой бизнес-модуль.

DB-каталог:

- принимает `AsyncSession` явным аргументом;
- не открывает и не коммитит транзакции;
- не вызывает S3, HTTP, RabbitMQ или TaskIQ;
- не импортирует `app.modules` и не знает о Courier, CourierDocument или
  другом бизнес-владельце;
- не вызывает `emit()`: бизнес-сервис сам пишет `FileConfirmed` в outbox в
  той транзакции, в которой File становится `ready`.

`storage` остаётся владельцем общего HTTP API файлов, правил их жизненного
цикла, S3-проверки, download/delete и фоновой очистки. Он использует общий
каталог вместо собственного ORM-определения. Временный реэкспорт классов из
`app.modules.storage.models` допустим только для совместимости импортов и
обнаружения metadata Alembic; второго ORM-mapping таблицы `files` быть не
должно.

Courier использует только `app.platform.files` и низкоуровневый streaming
uploader из platform. Это не передаёт ему общий файловый API: Courier вправе
лишь подготовить File для документа в своём агрегатном сценарии. `storage` не
импортирует Courier и не содержит relationship, FK или условие, зависящее от
таблиц Courier.

### Явное исключение для multipart Courier

`POST /courier` и добавление отдельного документа принимают байты через
backend и потоково передают их в S3. Это узкое, осознанное исключение из
правила direct-to-S3: без него требование «один запрос создаёт весь агрегат»
невыполнимо.

Исключение не меняет обычный `/files` flow. Для него сохраняются те же URL,
статусы и последовательность: сервер создаёт `pending` File и выдаёт
presigned URL, клиент загружает объект напрямую, `confirm` делает HEAD вне
транзакции и одной DB-транзакцией переводит File в `ready` вместе с
`FileConfirmed`.

Multipart Courier не становится новым универсальным upload endpoint. После
разбора формы байты читаются из `UploadFile` ограниченными частями, полный файл
дополнительно не накапливается в памяти, а незавершённый multipart upload в S3
abort'ится uploader'ом. При этом FastAPI/python-multipart может заранее
спулить request body во временный файл: это bounded-memory, но не настоящий
ingress-to-S3 streaming. Reverse proxy/ASGI ограничивает размер всего request,
а deployment учитывает требуемую ёмкость временного диска.

### Durable compensation через `FileUploadStaging`

Перед первым S3-вызовом для каждого входного файла создаётся
`FileUploadStaging`. Строка хранит заранее сгенерированный id будущего File,
`bucket`, `key`, исходное имя, состояние, `multipart_upload_id`, cleanup lease
и метаданные upload. Сохранённый bucket используется во всех S3-операциях;
текущий bucket из конфигурации не подменяет его.
Поэтому после падения процесса у фоновой очистки остаётся точный адрес объекта
и удаление не зависит от памяти процесса, `after_commit` или доставки задачи
через брокер.

Допустимы только такие переходы:

```text
uploading ───────▶ uploaded ───────▶ строка отсутствует
    │                 │             (поглощена успешной final transaction)
    └──────┬──────────┘
           ▼
       deleting ────────────────▶ строка отсутствует
                                  (S3 delete, затем DB delete)
```

Смысл состояний:

| Состояние | Смысл |
| --- | --- |
| `uploading` | Адрес зарезервирован; объекта ещё может не быть или upload оборвался |
| `uploaded` | S3 завершил upload; `size`, `content_type` и `etag` сохранены |
| `deleting` | Staging забран компенсацией; создавать по нему File запрещено |
| строки нет | Либо File атомарно создан, либо S3-объект уже удалён |

Переход `uploading → uploaded` выполняется условным UPDATE в отдельной короткой
транзакции. Если строка уже стала `deleting`, запрос не вправе финализировать
File и обязан закончиться ошибкой; дополнительный S3 delete допустим как
best-effort, но durable-маркер остаётся основным механизмом.

Просроченные `uploading` и `uploaded`, а также staging проигравшего
конкурентного создания переводятся в `deleting`. Периодическая задача TaskIQ
в процессе `worker.py` выбирает пачку через `FOR UPDATE SKIP LOCKED` и в той
же короткой транзакции записывает уникальный claim token и lease deadline.
Активный lease не выбирается другим worker; зависший `deleting` можно
claim'ить повторно только после expiry. Затем worker abort'ит незавершённый
multipart и удаляет объект из S3 без открытой транзакции, после чего удаляет
staging-строку условным DELETE по `id + token` в новой короткой транзакции.
Если процесс упал между созданием multipart upload и записью его id, cleanup
ищет uploads по точным `bucket + key` и abort'ит найденные. S3 abort/delete
идемпотентны; ошибка одного объекта оставляет строку `deleting` для следующего
прохода и не останавливает batch.

### Точная последовательность `POST /courier`

1. Handler разбирает форму, а сервис валидирует весь aggregate, нормализует
   email/phone и проверяет соответствие документов multipart-частям. До конца
   этой проверки нет ни DB write, ни S3-вызова.
2. Короткая read-only сессия ищет Courier по `email OR phone` и закрывается.
   Одно совпадение означает идемпотентный ответ `200` без upload; совпадение
   email и phone у разных Courier означает `409 identity-split`.
3. При отсутствии совпадений одна короткая DB-транзакция создаёт все staging
   rows в `uploading`. Она коммитится до первого обращения к S3.
4. Сервис потоково загружает каждый файл в S3 при закрытой DB-транзакции.
   После успешного upload фактические метаданные этого объекта записываются
   переходом `uploading → uploaded` в отдельной короткой транзакции.
5. Финальная DB-транзакция блокирует все staging rows в детерминированном
   порядке и требует состояние `uploaded`. Параллельная cleanup-задача не
   может одновременно поглотить те же строки.
6. Courier вставляется через natural-key conflict handling. Если конкурентный
   запрос уже создал Courier, эта ветка не создаёт File, Document, Account или
   outbox; все её staging rows становятся `deleting`, после коммита
   возвращается aggregate победителя с `200`.
7. Если вставка Courier успешна, та же транзакция создаёт все File сразу в
   `ready`, CourierDocument и CourierPlatformAccount, а также вызывает
   `emit(session, FileConfirmed(...))` для каждого File.
8. В той же транзакции удаляются использованные staging rows. Коммит либо
   одновременно сохраняет полный Courier aggregate, File и outbox и убирает
   staging, либо не сохраняет ничего из перечисленного.
9. Ответ `201` формируется только после успешного коммита. Если сбой случился
   до или во время финального коммита, staging остаётся для компенсации. Если
   соединение с клиентом оборвалось уже после коммита, компенсация не нужна:
   объекты имеют File и CourierDocument, а повтор по natural key вернёт
   сохранённый aggregate.

Немедленная попытка удалить S3-объекты после ошибки разрешена только как
оптимизация. Она не заменяет перевод staging в `deleting` и периодическую
очистку: процесс может упасть перед best-effort вызовом или во время него.

## Последствия

- Courier, его дочерние строки, File и `FileConfirmed` существуют по принципу
  «всё или ничего» внутри PostgreSQL; ложной атомарности между PostgreSQL и S3
  не обещается.
- Любой объект, загруженный до неуспешной final transaction, остаётся
  адресуемым через durable staging и может быть удалён после рестарта.
- `FileConfirmed` по-прежнему коммитится вместе с переходом File в `ready` и
  доставляется at-least-once через существующий outbox.
- `app.platform.files` становится общим контрактом для модулей. Поэтому его
  публичные классы и функции требуют полных докстрингов, строгой типизации и
  отдельных тестов границ транзакции.
- `storage` сохраняет знание о S3 и универсальной очистке, но теряет
  исключительное владение ORM-классом File. Изменение File теперь требует
  проверки всех использующих его модулей.
- Backend принимает байты только в aggregate endpoint Courier. Это расходует
  uvicorn worker и требует ограничений размера, количества документов,
  таймаутов и потоковой передачи; обычные большие или самостоятельные файлы
  продолжают идти напрямую в S3.
- Временные staging rows и периодическая задача увеличивают число состояний и
  операционную сложность. Нужны метрики возраста/числа `uploading`, `uploaded`
  и `deleting`, иначе остановившаяся компенсация останется незаметной.
- Физическая очистка имеет семантику at-least-once. Она безопасна благодаря
  условным переходам, `FOR UPDATE SKIP LOCKED` и идемпотентному S3 DELETE.

## Отвергнутые альтернативы

**Оставить File в `storage` и импортировать его из Courier.** Отвергнуто:
бизнес-модули начнут зависеть друг от друга, а `storage` неизбежно узнает о
Courier через обратные relationships и правила каскада.

**Создавать File через HTTP API `storage` или доменное событие.** Отвергнуто:
сеть внутри транзакции запрещена, а отдельный вызов или асинхронный подписчик
не может атомарно создать File вместе с CourierDocument и outbox до ответа.

**Дублировать File в Courier или писать raw SQL в таблицу `files`.** Отвергнуто:
два ORM-владельца разойдутся по constraints и lifecycle, а raw SQL создаст
скрытую зависимость на чужую схему без общего типизированного контракта.

**Держать PostgreSQL-транзакцию открытой во время S3 upload.** Отвергнуто:
долгий или зависший upload удерживает соединение и блокировки, но откат БД не
удаляет объект из S3. Транзакция становится дороже, не становясь общей.

**Сначала создать неполный Courier aggregate, затем загрузить и дописать
файлы.** Отвергнуто: другие запросы увидят частичное состояние, а упавший
upload потребует отдельного доменного статуса и сложного восстановления всего
агрегата.

**Очищать только best-effort вызовом, `after_commit` или `kiq()` из HTTP.**
Отвергнуто: падение процесса теряет callback или постановку задачи, а вызов
брокера нарушает запрет внешнего I/O в транзакции. Durable DB-состояние плюс
периодическая TaskIQ-задача переживают рестарт и временную недоступность S3.

**Перевести все загрузки на проксирование через backend.** Отвергнуто:
aggregate Courier требует одного исключения, но обычным файлам оно не даёт
преимуществ и зря занимает web workers, память и полосу backend.

**Распределённая транзакция между PostgreSQL и S3.** Отвергнуто: S3 не является
XA-ресурсом. Staging явно моделирует реальную семантику — атомарная DB-часть и
гарантированная компенсация внешнего объекта.
