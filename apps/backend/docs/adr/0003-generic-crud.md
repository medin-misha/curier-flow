# ADR 0003. Обобщённый `CRUD` допустим — и вот его границы

**Статус:** принято · **Дата:** 2026-08-10

## Контекст

Обобщённый репозиторий — классический антипаттерн. Он начинается с
`get/create/update/delete`, а заканчивается методом
`find(filters, joins, order_by, options)`, то есть переписанным на Python SQL,
который хуже читается и хуже оптимизируется, чем исходный запрос.

При этом без него первые пять модулей шаблона пишут одно и то же: `session.get`,
проверка на `None`, `raise NotFound`, `session.add`, `flush`, keyset-запрос со
своей реализацией курсора. Копия keyset-логики в каждом модуле — это пять
разных способов ошибиться в сравнении кортежей.

## Решение

`app.kernel.db.crud.CRUD` существует, но его набор **закрыт**:

| Метод | Что делает |
| --- | --- |
| `create(model, dto, session, **overrides)` | строка из схемы, `overrides` перекрывают поля |
| `get(model, pk, session)` | строка или `None` |
| `get_or_404(model, pk, session)` | строка или `NotFound` |
| `update(obj, patch, session, allowed=None)` | частичное обновление по белому списку |
| `delete(obj, session)` | физическое удаление |
| `list_page(model, session, page=..., where=())` | keyset-страница |

Ограничения зафиксированы и не обсуждаются:

- **Класс без состояния.** Сессия всегда приходит аргументом; экземпляра
  репозитория, привязанного к сессии, нет. Иначе появляется соблазн хранить в
  нём кеш и «текущего пользователя».
- **Никаких join, агрегатов, батчей, произвольных фильтров.** Единственная
  уступка — `where` в `list_page`: последовательность готовых условий
  SQLAlchemy, а не собственный язык фильтров. Всё сложнее пишется запросом в
  `services.py` — там, где видно, какой именно SQL уедет в базу.
- **Никакого мягкого удаления флагом.** `delete` удаляет физически. Мягкое
  удаление — это обновление `deleted_at`, и делает его сервис: решение «строку
  можно потерять» слишком важное, чтобы прятать его за параметром общего метода.
- **Вызывать `CRUD` вправе только `services.py`.** Хендлер, дошедший до CRUD в
  обход сервиса, обходит вместе с ним и все бизнес-правила. Проверяет это
  `tests/test_architecture.py::test_handlers_never_import_crud`.
- **`update` работает по белому списку `__patchable__` модели.** Поле вне
  списка — `Conflict`, а не тихая фильтрация: клиент, попросивший сменить
  `status`, должен узнать, что этого не произошло.
- **Серверные значения идут через `**overrides`, а не через схему запроса.**
  Владелец, начальный статус, сгенерированный ключ в схеме отсутствуют — иначе
  клиент сможет их подменить.

## Последствия

- Модуль из одной таблицы пишется без единого запроса SQL.
- Как только появляется join или агрегат, автор пишет обычный `select()` —
  и это видно в diff, а не спрятано за параметром общего метода.
- Keyset-пагинация реализована один раз; ошибка в сравнении кортежей возможна
  только в одном месте.
- `create` делает `flush()`, поэтому `id` и `created_at` доступны сразу — в том
  числе для `emit()` в той же транзакции.
- Расширять `CRUD` нельзя без пересмотра этого ADR. Появление в нём параметра
  `filters` или `join` означает, что решение изменилось, — тогда меняется и
  документ.

## Альтернативы

**Репозиторий на каждую сущность (`OrderRepository`).** Честный DDD-вариант.
Отвергнут: на первых модулях это пять классов с одинаковыми телами, а разница
между ними появляется в одном методе из десяти. Когда у сущности действительно
своя логика доступа, она пишется запросом в сервисе — и это дешевле класса.

**Голый SQLAlchemy без обёрток.** Максимально прозрачно, но копирует
keyset-логику и обработку «нет строки → 404» по всем модулям. Проиграл именно
на этих двух местах.

**Готовая библиотека (`fastapi-crudrouter` и подобные).** Генерируют ручки по
модели. Отвергнуто: они генерируют ещё и слой API, вместе с ним — прямой путь
от HTTP к таблице в обход сервиса, а это ровно то, что запрещено в шаблоне.
