# ADR 0006. Пишущая транзакция объявляется с `scope="function"`

**Статус:** принято · **Дата:** 2026-08-10

## Контекст

Транзакцию запроса держит зависимость с `yield`:

```python
async def get_uow() -> AsyncIterator[AsyncSession]:
    async with session_factory() as session:
        async with session.begin():
            yield session
        await _run_after_commit_hooks(session)
```

Коммит происходит на выходе из блока, то есть при закрытии генератора. **Момент,
в который фреймворк закрывает зависимость, задаёт фреймворк, а не мы.**

По умолчанию у зависимостей с `yield` область `request`: FastAPI закрывает их
**после того, как ответ отправлен клиенту**. Последовательность получается
такая:

```
обработчик вернул 201 → тело ушло в сокет → get_uow пробует COMMIT → COMMIT упал
                                          → исключение попадает в лог
```

Клиент видит 201 и считает заказ созданным. В базе заказа нет. Причины упавшего
коммита совершенно обыденные: нарушенное отложенное ограничение
(`DEFERRABLE INITIALLY DEFERRED`), дедлок, обрыв соединения с базой,
исчерпание диска.

## Решение

```python
Uow = Annotated[AsyncSession, Depends(get_uow, scope="function")]
```

С областью `function` FastAPI закрывает зависимость сразу после того, как
обработчик маршрута вернул готовый ответ, но **до его отправки**. Упавший
коммит превращается в обычное исключение, а его обрабатывает `app/api/errors.py`
и отдаёт 500 в формате problem+json.

Правило распространяется на **все** объявления, а не только на `app/api/deps.py`:
бизнес-модулю запрещено импортировать слой `api`, поэтому он объявляет свой
псевдоним из той же функции ядра — и вместе со строкой дублируется способ
ошибиться.

`RoSession` остаётся с областью по умолчанию сознательно: транзакции у неё нет,
коммита тоже, ломаться при закрытии нечему, а сессия, живущая до конца отправки,
оставляет возможность отдавать ответ потоком.

## Последствия

- «2xx на несохранённые данные» невозможно.
- Обвязка `Idempotency-Key` не страдает: `IdempotentRoute` — часть обработчика
  маршрута, то есть выполняется **внутри** этой области, и ответ по-прежнему
  дописывается в ту же транзакцию, что и данные с ключом.
- Потоковый ответ (`StreamingResponse`), читающий курсор по мере отправки,
  через `Uow` невозможен: транзакция закроется раньше первого байта. Для чтения
  есть `RoSession`, для записи потоковый ответ бессмыслен.
- Один забытый `scope` в новом модуле снимает инвариант целиком и молча.
  Поэтому правило проверяется разбором исходников:
  `tests/test_architecture.py::test_uow_dependencies_close_before_the_response`
  падает на любом `Depends(get_uow)` без области, в любом файле.
- Сам инвариант проверяется от поведения, а не от кода:
  `tests/test_commit_before_response.py` поднимает **настоящий uvicorn** и
  ломает `COMMIT` отложенным ограничением Postgres. `ASGITransport` здесь не
  годится — он собирает ответ целиком и лишь потом решает судьбу исключения,
  поэтому «клиент уже получил 2xx» и «клиент получил 500» на нём неразличимы.

## Альтернативы

**Коммитить в обработчике или в сервисе.** Убирает проблему момента закрытия,
но возвращает `session.commit()` в бизнес-код: одна атомарная операция
распадается на несколько, откат перестаёт откатывать, а забытый коммит на
какой-нибудь ветке кода обнаруживается в проде.

**Middleware, которое коммитит.** Middleware не знает, какая сессия относится к
запросу, и выполняется вокруг всего стека — включая формирование потокового
ответа. Тот же порядок «ответ ушёл → коммит».

**Коммит вручную в конце каждой ручки.** То же, что и первый вариант, плюс
обязанность помнить об этом в каждой из них.

**Оставить `scope="request"` и логировать сбой.** Именно этого мы и избегаем:
запись в логе не отменяет 201, уже полученного клиентом.
