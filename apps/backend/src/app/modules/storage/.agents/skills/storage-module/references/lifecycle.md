## Жизненный цикл файла

```
                POST /files/upload-url
                        │  (транзакция закоммичена ДО выдачи ссылки)
                        ▼
                    ┌────────┐   PUT по ссылке   ┌──────────────┐
                    │pending │ ────────────────▶ │ объект в S3  │
                    └────────┘                   └──────────────┘
                     │      │
   POST .../confirm  │      │  клиент пропал, TTL истёк
   HEAD + сверка     │      │  (sweep_orphaned_uploads)
                     ▼      ▼
                 ┌───────┐  ┌──────────┐
                 │ ready │  │ deleting │◀── DELETE /files/{id}
                 └───────┘  └──────────┘
                     │            │  delete_marked_files:
                     └────────────┘  сначала объект, потом строка → строки нет
```

Кто меняет статус:

- `pending` ставит `create_upload` — единственное место, где строка рождается;
- `ready` ставит `confirm_upload` в одной транзакции с `emit(FileConfirmed)`;
- `deleting` ставит `mark_for_deletion` (ручка DELETE) или сборщик сирот,
  когда `pending` пережила `STORAGE_ORPHAN_TTL`;
- строку удаляет только `delete_marked_files`, и только после того, как объект
  в хранилище удалён.

Из `deleting` возврата нет. `confirm` и `GET` на таком файле отвечают **404**:
ответив на DELETE, сервис пообещал, что файла больше нет, и остальные ручки
обязаны отвечать так же. Воскрешение строки дало бы `ready` без содержимого —
задача уже удаляет объект.
